Pipeline 1: Problemas reales
Problema 1 — El merge por difflib es frágil para textos legales
difflib.SequenceMatcher mide similitud de caracteres, no semántica. Dos cláusulas pueden ser 94% similares en caracteres pero normativamentediferentes (una dice "hasta 5%" y otra "hasta 3%"). Y lo contrario: dos cláusulas semánticamente equivalentes escritas diferente pueden no mergearse cuando deberían.

El threshold 0.95 es muy alto — casi solo captura duplicados exactos con diferencias de whitespace. Probablemente hay clusters que deberían mergearse pero no lo hacen porque la redacción varía más.

Mejora concreta: Después del merge por texto, agregar un segundo pass de merge por distancia de embeddings. Si el centroide de dos clusters tiene cosine similarity > 0.92 (threshold empírico, ajustable), mergear. Esto ya tenés los embeddings calculados, es barato.

Problema 2 — El schema diseñado sobre 5,000 muestras puede no cubrir variantes raras
K-Means con 5,000 muestras de 31,000 puede no capturar clusters que solo existen en el 2-3% del corpus total pero que son los más anómalos. Un cluster de 620 documentos (2% de 31,000) puede quedar fuera del sample de 5,000 o representado con tan pocas muestras que el LLM no lo detecta.

Mejora concreta: Stratified sampling en lugar de random sampling. Si el título tiene 31,000 secciones y sampleás 5,000, no hagas random — hacé clustering primero sobre el sample y luego verificá que los clusters pequeños del sample correspondan a clusters reales en el corpus completo. Una validación simple: después de K-Means sobre 5,000, asignar las 26,000 restantes al cluster más cercano y verificar que la distribución no cambie más de un 15%.

Problema 3 — La truncación dinámica puede cortar exactamente donde está la anomalía
median_text_length × 1.5, clamp [500, 2000]. Para "fraude y corrupcion" con textos de ~1,984 chars en promedio, el límite queda en ~2,000 — que coincide con el máximo del clamp. Pero si el texto tiene 2,500 chars y la cláusula anómala está al final (común en documentos legales donde las excepciones van al cierre), la truncación la elimina.

Mejora concreta: Para el prompt de Pipeline 1 (schema design), truncar por el final es aceptable porque estás viendo distribuciones. Para Pipeline 2 (extracción), truncar por el final es un error de diseño. En build_section_extraction_prompt el texto debería ir completo o con una estrategia de chunking diferente (por ejemplo, si el texto supera el límite, incluir siempre los últimos 300 chars además de los primeros N).

Pipeline 2: Problemas reales
Problema 1 — response_format: json_schema asume que el LLM soporta structured outputs
Tu LocalLLMProvider usa LM Studio con Qwen 2.5 14B. LM Studio soporta json_object pero el soporte de json_schema (con validación contra un schema específico) depende de la versión y el backend. Si usás json_schema y el modelo no lo soporta, el fallback silencioso puede devolver JSON malformado que pasa json_object pero no el schema.

Mejora concreta: Tener dos paths en el transformer:

Si el provider soporta json_schema: usarlo con el schema derivado del master schema
Si no: usar json_object + validación post-LLM en _validate_extraction()
La validación post-LLM es necesaria de todas formas, así que no es trabajo extra — solo no asumir que el formato garantiza correctitud de tipos.

Problema 2 — El paralelismo con semaphore sobre LM Studio es un cuello de botella no obvio
6 workers concurrentes sobre un solo proceso de LM Studio con Qwen 14B en una 4070 Ti SUPER de 16GB va a saturar la VRAM en el primer request grande. LM Studio no es thread-safe para múltiples requests simultáneos de la misma forma que un servidor de producción — los requests se encolan internamente pero el KV cache se fragmenta entre ellos.

En la práctica con un modelo 14B en 16GB VRAM, el throughput real con 6 workers concurrentes probablemente sea similar o peor que 2-3 workers. El cuello de botella es la inferencia secuencial en GPU, no el I/O.

Mejora concreta: Antes de correr las 315,000 secciones, hacer un benchmark de 100 secciones con 1, 2, 3, 4 workers y medir tokens/segundo. Para un 14B en esa GPU, el punto óptimo probablemente sea 2-3 workers, no 6. Con el 7B Q4 podría ser diferente.

Alternativamente, si querés verdadero paralelismo local, levantar dos instancias separadas de LM Studio en puertos distintos (1234 y 1235) con el 7B cada una — eso sí usa la VRAM en paralelo real.

Problema 3 — El fallback de defaults silenciosos contamina Pipeline 3
|-> si falla: fallback defaults (0 para binarios, 0 para numéricos)
Si una sección de 1,984 chars falla la extracción y guardás todo en 0, Pipeline 3 (Isolation Forest) va a ver ese registro como "completamente vacío de contenido normativo" — que es una anomalía de nivel máximo. Pero en realidad es un fallo de extracción, no una anomalía real.

Mejora concreta: Agregar una columna extraction_confidence a la tabla destino y un flag is_fallback: bool. Los registros con is_fallback=True se excluyen del entrenamiento de Pipeline 3 o se tratan como missing values, no como ceros reales.

Problema 4 — No hay validación de consistencia del schema entre corridas
El schema_version en la tabla es un string libre. Si regenerás los schemas de Pipeline 1 (por ejemplo, con una mejora del prompt), las filas antiguas en section_extracted_features tienen campos que ya no corresponden al schema nuevo. Pipeline 3 podría mezclar features de versiones distintas del schema.

Mejora concreta: El schema_version debe ser un hash del schema (MD5 o SHA1 de los field names + types). Antes de hacer UPSERT, verificar que el schema_version coincide con el de las filas existentes para ese título. Si no coincide, hay dos opciones: borrar las filas viejas del título o levantar un error explícito.

python
import hashlib, json

def compute_schema_version(schema: dict) -> str:
    # Solo fields + types, no descriptions ni hints (esos pueden cambiar sin romper compatibilidad)
    canonical = {k: v["type"] for k, v in schema.items()}
    return hashlib.md5(json.dumps(canonical, sort_keys=True).encode()).hexdigest()[:8]
